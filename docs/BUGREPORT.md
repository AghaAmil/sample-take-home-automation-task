# Bug Report

## BUG-001

| Field | Details |
| --- | --- |
| Defect ID | BUG-001 |
| Title | Authentication error message remains in English after switching the application language to Persian |
| Severity/Priority | **Severity:** Medium. The user can continue using the application, but the selected language state is inconsistent and a user-facing validation message is not localized. **Priority:** Medium, because it affects the Persian language behavior covered by TC-12 and auth validation flows TC-03, TC-04, TC-06, and TC-09. |
| Environment | **Browser:** Desktop browser used for manual functional testing; exact browser is not visible in the provided screenshot. **OS:** macOS desktop environment. **Viewport:** approximately 700 x 527 px based on the provided evidence image. **App launch method:** local static `index.html`, consistent with the test plan environment. **Language/theme:** switched from English to Persian, light theme. |
| Preconditions | Browser local storage is cleared or the app is in a known authentication state. The application is open on the authentication screen in English. For the provided evidence, the app is in Login mode and no account exists for the entered player name. |
| Steps to Reproduce | 1. Open `index.html` in a desktop browser.<br>2. Keep the application language set to English.<br>3. Navigate to an authentication flow that can show a validation error. For example, click `Already have an account? Log in`.<br>4. Trigger an authentication error. For example, enter a player name that has not been registered and click `Log In`.<br>5. Confirm the English error message is displayed: `No account with this name. Please register.`<br>6. Change the language selector from `English` to `Persian`.<br>7. Observe the authentication screen and the displayed error message. |
| Expected Result | All visible authentication UI text updates to Persian after the language selector is changed. The existing validation error should also be translated to the Persian equivalent for the active error state, or the stale error should be cleared so an English message is not shown in the Persian UI. |
| Actual Result | The page direction and most authentication labels/buttons switch to Persian, but the existing validation error remains in English: `No account with this name. Please register.` This creates a mixed-language authentication screen. |
| Evidence | [Screenshot: Persian authentication screen with English error message](media_attachment/bug-001-auth-error-language-persian.png). |
| Notes | Frequency: reproducible whenever an auth error is displayed before changing the language to Persian. This likely affects all authentication errors that are stored as rendered text, including empty name, too-short name, duplicate account, and unknown account errors. Suspected area: `index.html` keeps `authError` as a localized string and the language-change render path does not recalculate the active error from a stable error key. Workaround: change language first, then trigger the validation error again. |

## BUG-002

| Field | Details |
| --- | --- |
| Defect ID | BUG-002 |
| Title | Hard difficulty computer move can overwrite an occupied player cell and incorrectly win the match |
| Severity/Priority | **Severity:** High. This breaks core Tic-Tac-Toe board rules, invalid move prevention, and result detection during gameplay. **Priority:** High, because it affects the primary Play flow and overlaps with critical gameplay coverage in TC-15, TC-16, TC-19, and TC-25. |
| Environment | **Browser:** Desktop browser used for manual functional testing; exact browser is not visible in the provided video. **OS:** macOS desktop environment. **Viewport:** approximately 694 x 770 px based on the generated video preview. **App launch method:** local static `index.html`, consistent with the test plan environment. **Language/theme:** English, dark theme. **Game state:** logged in as `Amir`, Play view, Hard difficulty selected. |
| Preconditions | A user account exists and the user is logged in. The Play view is displayed. Hard difficulty is selected before or during a new game. The board is in an active game state with at least one player `X` and one computer `O` already placed. |
| Steps to Reproduce | 1. Open `index.html` in a desktop browser.<br>2. Create or log in to a user account.<br>3. On the Play view, set the difficulty selector to `Hard`.<br>4. Start a new game if needed so the board is empty and the status shows `Your turn (X)`.<br>5. Play the Hard difficulty game by selecting empty cells and waiting for each computer move.<br>6. Continue until the board reaches the state shown in the attached screen recording.<br>7. On the player's turn, select an available empty cell.<br>8. Wait for the computer move and observe whether the computer places `O` only in an empty cell. |
| Expected Result | Hard difficulty should follow the same board integrity rules as every other difficulty. The player-selected `X` cells must remain unchanged, the computer must place `O` only in an empty cell, and the game result should be calculated only from legal board states. Hard difficulty should also be at least as capable as Medium and should not make illegal moves. |
| Actual Result | In the provided recording, a cell previously selected by the player is selected again by the computer. The player's cell is overwritten with `O`, creating an illegal board state, and the application then declares a computer win. This makes Hard difficulty appear less reliable than Medium and causes an invalid loss for the player. |
| Evidence | [Screen recording: Hard difficulty overwrites a player-selected cell](media_attachment/bug-002-hard-difficulty-overwrites-player-cell.mov). |
| Notes | Frequency: observed during manual functional testing with Hard difficulty. Suspected area: the Hard difficulty/minimax path in `index.html` appears to cache board evaluations using `board.join('')`, which can produce the same cache key for different board layouts because empty cells are removed from the joined string. The computer move handler then writes `O` to the returned index without verifying that the target board cell is still empty. Recommended validation: add an automated test that asserts the computer never changes an occupied `X` or `O` cell and that all Hard moves target indexes from the current empty-cell list. Workaround: use Easy or Medium difficulty until Hard move selection is fixed. |

## BUG-003

| Field | Details |
| --- | --- |
| Defect ID | BUG-003 |
| Title | Get Hint highlights occupied or strategically incorrect cells and can mislead the player |
| Severity/Priority | **Severity:** Medium. The core game can continue, but the hint assistance feature is unreliable and can provide invalid guidance during active gameplay. **Priority:** Medium, because it directly fails the hint behavior covered by TC-23 and can reduce confidence in the Play flow. |
| Environment | **Browser:** Desktop browser used for manual functional testing; exact browser is not visible in the provided videos. **OS:** macOS desktop environment. **Viewport:** approximately 694 x 770 px in the May 15 video preview and 777 x 874 px in the May 16 video preview. **App launch method:** local static `index.html`, consistent with the test plan environment. **Language/theme:** English UI; evidence includes dark theme with Medium difficulty and light theme with Easy difficulty. |
| Preconditions | A user account exists and the user is logged in. The Play view is displayed. A game is active, it is the player's turn, and the `Get Hint` button is enabled. The board has a partially completed state with at least one empty cell available. |
| Steps to Reproduce | 1. Open `index.html` in a desktop browser.<br>2. Create or log in to a user account.<br>3. Start a game on the Play view.<br>4. Select a difficulty such as `Easy` or `Medium`.<br>5. Make several player moves and wait for each computer move so the board contains both `X` and `O` marks.<br>6. When the status shows `Your turn (X)`, click `Get Hint`.<br>7. Observe which cell receives the hint highlight.<br>8. Continue using the suggested hint and observe whether it supports a valid player move or leads to a losing path. |
| Expected Result | `Get Hint` should highlight one currently empty and playable cell. The suggested cell should be a valid recommendation for the player and should not identify an already occupied `X` or `O` cell. The hint should clear after the expected short timeout without changing the board state. |
| Actual Result | The hint highlight can appear on an already occupied cell, including a cell containing `O` in the provided evidence. The suggested move is not reliable and can guide the player into a losing path instead of providing useful assistance. |
| Evidence | [Screen recording: Hint provides unreliable guidance on Medium difficulty](media_attachment/bug-003-hint-unreliable-medium.mov). [Screen recording: Hint highlights an occupied cell on Easy difficulty](media_attachment/bug-003-hint-highlights-occupied-cell-easy.mov). |
| Notes | Frequency: observed in multiple manual functional testing recordings and across more than one difficulty. Suspected area: `index.html` appears to calculate hints through the same minimax helper used by Hard difficulty. That helper caches board evaluations using `board.join('')`, which can collide for different board layouts, and the hint handler does not validate that the returned index is currently empty before assigning the hint highlight. Recommended validation: add an automated test for TC-23 that sets up multiple board states and asserts that `Get Hint` always highlights one index from the current empty-cell list. Workaround: avoid relying on `Get Hint` until hint selection validates playable cells and uses a correct recommendation algorithm. |

## BUG-004

| Field | Details |
| --- | --- |
| Defect ID | BUG-004 |
| Title | Account and profile name fields accept special characters and excessive length, causing layout issues |
| Severity/Priority | **Severity:** Medium. The app remains usable in some cases, but invalid or excessive user names create incorrect UI state and visible layout breakage. **Priority:** Medium, because this affects account creation, profile management, and navigation display quality covered by TC-05, TC-30, and TC-31. |
| Environment | **Browser:** Desktop browser used for manual functional testing; exact browser is not visible in the provided screenshots. **OS:** macOS desktop environment. **Viewport:** approximately 1316 x 1514 px in the special-character screenshot and 1646 x 1402 px in the long-name screenshot. **App launch method:** local static `index.html`, consistent with the test plan environment. **Language/theme:** English UI, dark theme. |
| Preconditions | Browser local storage is cleared or the app is in a known state. The application is open on the authentication screen for account creation, or the user is logged in and the Profile view is available for display name modification. |
| Steps to Reproduce | 1. Open `index.html` in a desktop browser.<br>2. In Create Account mode, enter a name made of special characters, such as `###`.<br>3. Click `Create Account`.<br>4. Observe the created account name, avatar, greeting, and navigation layout.<br>5. Open the Profile view.<br>6. Change the display name to a very long value, for example a long string with many words or characters.<br>7. Click `Save Changes`.<br>8. Observe the navigation bar, profile form, action buttons, and page layout. |
| Expected Result | Account creation and profile name update should validate user names beyond minimum length. Names should have a reasonable maximum length and either restrict unsupported special-character-only values or safely normalize them. If long names are allowed, all rendered locations should truncate, wrap, or constrain the text without pushing navigation, buttons, forms, or page content outside the intended layout. |
| Actual Result | The application accepts special-character-only names such as `###` and displays them in the avatar/greeting. It also accepts very long profile names. After saving a long name, the navigation bar and profile content expand beyond the intended application container, controls shift out of alignment, and the layout becomes visually broken. |
| Evidence | [Screenshot: Special-character account name accepted](media_attachment/bug-004-special-character-account-name.png). [Screenshot: Long profile name breaks layout](media_attachment/bug-004-long-profile-name-layout-break.png). |
| Notes | Frequency: reproducible during account creation and profile name modification. Suspected area: `index.html` appears to enforce only a minimum length on the auth and profile name inputs; no visible maximum length, character pattern, or defensive rendering constraint is applied for long display names. Recommended validation: add boundary tests for special-character-only names, leading/trailing whitespace, maximum accepted length, and long-name rendering in the navigation and profile views. Workaround: manually use short alphanumeric names until validation and UI constraints are added. |
